DEADLOCK — architecture (as built, 22 Oct evening)
=================================================

One laptop runs everything. No database: state is in memory.
Grok does language. Code does logic. Grok never decides if the plan is viable.

The idea: sign up once by scanning a WhatsApp QR. After that, tag @deadlock in
any group chat. Deadlock reads the chat, works out who is waiting on whom,
posts "it's stuck, here's why" with a link to the stage, nudges the bottleneck
person, and posts "It's on!" when everything unlocks.

2. SIGN UP  (the page at /, Ali's onboarding flow: landing → sign up → scan → live)
-----------------------------------------------------------------------------------

  / ── "Sign up" ──► server: reset demo ──► bridge /api/reset
                     (unlink the old WhatsApp, wipe its store, restart)
  / ◄── QR ── server ◄── bridge /api/status { qr }
  scan in WhatsApp → Settings → Linked devices → Link a device
  / shows "Sign up complete! Type @deadlock in any WhatsApp group."

  Every sign-up is a fresh session: old link, old chats, old plan, all gone.


3. LIVE FLOW
------------

  (a) trigger
      someone writes "@deadlock ..." in any chat (only messages < 2 min old count)
      ─► server starts a plan on THAT chat: loads its last 30 messages, names
         from bridge /api/names, stage heading "WHATSAPP · <chat name>"

  (b) understand (Grok, ~1-2s)
      llm.detectAndExtract(messages around the tag)
        ─► plan { title, requiredForPlan } + commitments, each with exact quote:
           "I'll host if someone brings pizza"  → Ali   offers venue     if food
           "I'll come if someone hosts"         → Sam   offers attendees if venue
           "I'll bring pizza"                   → Mehdi offers food
        a proposal with no replies yet is still a plan (0 commitments)
        output is checked against the chat: real people, real quotes

  (c) decide (code, instant)
      solver.solve() ─► unlock order, viable?, blocking[]
      attendees = people whose "I'll come" has unlocked

  (d) report
      stuck  ─► Grok explains in one sentence (streamed to the stage)
             ─► bot posts in the chat:
                🤖 *Deadlock bot*
                Pizza Thursday is stuck. <why>. Watch it unlock: https://…/stage
      viable ─► straight to (g)

  (e) keep listening
      each new message in that chat (batched 2s) ─► llm.extractDelta
        ─► new / changed / withdrawn commitments, or an answer to the bot
        ─► solver ─► stage updates

  (f) the agent breaks the deadlock
      stuck with no change for 10s ─► llm.negotiate
        ─► picks the bottleneck, proposes loosening ONE existing condition
        ─► code checks it really only loosens ─► bot posts the question in the chat
      "yeah 12 is fine" ─► extractDelta reads it as yes
        ─► code applies the change ─► solver ─► cascade

  (g) booked
      solver: viable ─► stage cascade, then llm.book
        ─► event (title, when, where, 4-item agenda, blurb)
        ─► bot posts "It's on! <event> https://…/stage"

5. FALLBACKS  (the show must run with the wifi off)
---------------------------------------------------

  Grok slow/down or MOCK_LLM=true  ─► llm/mocks.ts (matches the seeded chat)
  No WhatsApp / bridge down        ─► seeded chat from seed.ts, driven from /admin
  Agent stalls                     ─► /admin: "negotiate", then "Yes"
  Any step fails                   ─► /admin: force each step by hand
  Tunnel restarts                  ─► new URL; links already posted in WhatsApp break,
                                      so start it once and leave it


6. KNOWN LIMITS
---------------

  - One live plan at a time: the latest chat to tag @deadlock.
  - The bot posts as whoever signed up (use a spare number on stage).
  - Grok sees only the chat that tagged @deadlock, never the others.
  - The audience QR join (/join) still works but is optional now.
